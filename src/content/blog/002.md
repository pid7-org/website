How TurboFox's embedded key-value database moved from a conventional hash table to a
radix-trie index to avoid expensive global rehashing.

When I started working on my own key-value database, I spent quite some time looking
at different storage architectures. Eventually, I settled on a single-file storage
layout, with the entire file mapped into memory using `mmap` syscall. The core idea
was to keep the storage structure self-contained[^1] while keeping the reads and
writes as efficient as possible.

After finalizing storage structure, we need a way to locate entries without scanning
the entire file. For that, a hash table seemed like a pretty obvious choice. It gives
us expected O(1) lookup in the number of stored entries, assuming a reasonable hash
distribution and load factor. The index only needs to keep track of the hash and
where the actual key-value payload lives, rather than storing the payload itself.

Everything seemed pretty straightforward. We had our storage layout, we had our
index, and we could efficiently locate entries. But as the database grows, so does
the index. And growing a hash table isn't quite as cheap as using one.

## § Hash Tables

If you've worked with hash maps in Rust, you're probably already familiar with how a
hash table works. Given a key, we first calculate its hash and use that hash to
determine which bucket the entry belongs to. Instead of looking through every
existing entry, we can jump directly to the bucket we're interested in.

In TurboFox, the index keeps the hash of an entry along with an offset pointing to
its actual key-value payload. Of course, two different keys can produce the same hash
or end up in the same bucket. That's why we still need to verify the actual key
before considering an entry a match.

<fig>
Key ("name")
       |
       +---> hash("name") = 0x7A91...
                   |
                   +---> hash % 4 = Bucket 2
                                       |
  Index (Hash Table)                   v
  +------------+-----------+-----------------------+-----------+
  | Slot 0     | Slot 1    | Slot 2                | Slot 3    |
  | [   x   ]  | [   x   ] | [ 0x7A91... | @4096 ] | [   x   ] |
  +------------+-----------+-----------------------+-----------+
                                       |
                                       | offset
                                       |
                                       v
                             +--------------------+
                             | "name" : "turbofox"|
                             +--------------------+

@desc A key is hashed and mapped to a specific bucket, which stores the hash and an
offset pointing to the raw bytes stored in storage
</fig>

The nice part is that we don't have to search through the entire database. With a
reasonably distributed hash function and a controlled load factor, we get expected
O(1) lookup complexity with respect to the number of entries.

For a key-value database like [TurboFox](https://github.com/pid7-org/turbofox),
that's pretty much what we want. But as more entries are inserted, the table starts
filling up. Eventually, we need more room to accommodate new entries while keeping
lookups efficient.

Sounds great, right? There's just one problem.

## § Global Rehashing

The conventional way to grow a hash table is to increase its capacity and
redistribute all the existing entries. When a hash table gets too full, we allocate
a larger table, iterate over the existing entries, calculate their new bucket
positions and insert them into the new table. Once everything has been moved, we can
discard the old table.

This operation is commonly called _rehashing_.

<fig>
set(K4) ---> Table Full
                 |
                 v
  Old Table (Capacity = 4, hash % 4)
  +--------+--------+--------+--------+
  | Slot 0 | Slot 1 | Slot 2 | Slot 3 |
  | [ K0 ] | [ K1 ] | [ K2 ] | [ K3 ] |
  +--------+--------+--------+--------+
      |
      | Recompute (hash % 8) for ALL entries
      |
      v
  New Table (Capacity = 8, hash % 8)
  +--------+---------+--------+--------+---------+--------+--------+---------+
  | Slot 0 | Slot 1  | Slot 2 | Slot 3 | Slot 4  | Slot 5 | Slot 6 | Slot 7  |
  | [ K0 ] | [  x  ] | [ K4 ] | [ K1 ] | [  x  ] | [ K3 ] | [ K2 ] | [  x  ] |
  +--------+---------+--------+--------+---------+--------+--------+---------+

@desc Inserting a single key into a full hash table triggers a global rehash, forcing
every existing entry to be recomputed and moved to a new slot
</fig>

The problem is that this operation scales with the total number of entries in the
table, not the number of entries involved in the current insertion. Most insertions
are relatively cheap, but occasionally, one insertion triggers a complete index
rebuild.

In textbook terms, this usually isn't considered a problem. The cost of rehashing can
be spread across subsequent insertions, giving amortized O(1) time complexity for
`set(key, value)` operations. And technically, that's correct.

But in real world time complexity and operational latency aren't quite the same
things.

Imagine performing 100 insertions. 99 of them take 1 µs, while one takes 101 µs
because it triggered a global rehash. The average latency is just 2 µs, which sounds
pretty good. But one insertion still took 101 times longer than the others.

This is exactly the kind of behavior that average latency tends to hide. When we're
interested in how a database feels under real workloads, the upper percentiles like
**p99** and even **p99.9** matters just as much as the median i.e. **p50**. A sudden
spike in insertion latency can show up in the **p99** and **p99.9** percentiles,
depending on how frequently rehashing occurs.

For TurboFox, this is particularly undesirable. Being an embedded database, it runs
inside the same process as the application using it. A long-running operation isn't
just another benchmark number; it can mean a lagging UI or a command that suddenly
takes much longer than expected.

Memory mapping doesn't make this problem disappear either. Even though the index
lives in mapped storage, redistributing its entries still requires visiting the
existing entries and rebuilding their layout.

We wanted to keep the fast lookup behavior of a hash table without occasionally
turning a cheap `set(key, value)` call into an operation that has to deal with the
entire index.

_So, how do we grow a hash table without having to rebuild the whole thing?_

## § A Tale of Tail Latency

So far, the understanding is, a call like `set(key, value)` which is usually cheap
but occasionally needs to deal with entire index, explodes the tail latency for the
said operation.

But that also made me question, _how are we going to optimize for tail latency, more
specifically the **p99.9** latency ?_

A hash table gives us excellent avg-case behavior. Most operations are cheap, and
that's exactly why it's such a common choice for key-value storage engines. But
average latency doesn't tell the whole story. If almost every operation takes 1 µs
and one out of every thousand takes 100 µs, the average can still look pretty
reasonable while that one operation feels terrible, _mainly to the user_.

For an embedded database like [TurboFox](https://github.com/pid7-org/turbofox), we
must care about what happens at the tail of the distribution. In particular, we want
the **p99.9** latency to stay reasonably close to the typical latency rather than
having occasional operations run orders of magnitude slower.

_The solution is to make the global rehashing less painful._

One way is incremental rehashing, where we move only a few entries at a time instead
of rebuilding the entire table in one operation. That certainly makes the individual
spikes smaller, but now we have to deal with entries living in two tables while the
migration is in progress, keep track of migration state, and make sure that state is
recoverable if the process is interrupted (which, unfortunately, is very likely with
an embedded database).

Other solution is, we avoid rehashing entirely by adding overflow buckets when a
bucket becomes full.

<fig>
Index (Fixed Table)             Chained Overflow Buckets (Linear Scan)
  +------------+
  | Bucket 0   |-----------> +------------+ ------------> +---------------+
  | [Full: 32] |    next     | Overflow 1 |     next      | Overflow 2    |
  +------------+             | [Full: 32] |               | [ K99 |  x  ] |
  | Bucket 1   |             +------------+               +---------------+
  | [   x   ]  |                   ^                              ^
  +------------+                   |                              |
                             hop 1 (scan 32)                hop 2 (found K99)

@desc When a primary bucket fills up, new entries are appended to a linked chain of
overflow buckets, turning a direct lookup into a sequential multi-bucket scan
</fig>

That makes growth local, but the lookup path can now grow with the overflow chain.
The operation that was supposed to be a quick lookup can end up walking through
several buckets[^2].

Neither approach really solved the problem for us. We do not want to make rehashing
slightly less expensive. _We wanted to avoid having unrelated parts of the index
participate in growth at all_, hence keeping the lookup path predictable.

So instead of asking ~How can we make a hash table resize better?~, I started asking
a slightly different question.

**What if we didn't have to resize the hash table in the first place?**

## § A Different Approach

So instead of using the hash to pick a bucket for the entry in one large table, we
started using parts of the hash to navigate a tree. The leaves of that tree would
still be our hash buckets, but now each bucket could grow independently.

We take the 32 bit hash and consume it in small four bit pieces. Each piece tells us
which child to follow until we eventually reach a leaf bucket.

<fig>
Key ("name") ---> XXHash32 ---> 0x7A91_04C2 
                                   |
                                   |  Slice 4-bit nibbles (LSB to MSB)
                                   |
                                   v
                           [0x2] [0xC] [0x4] ...
                             |     |
                             |     +-------------------+
                             v                         |
                       Depth 0 (Root Node)             v
                       +----+----+----+----+     Depth 1 (Routing Node)
                       | 0  | 1  | 2  | .. |     +----+----+----+----+
                       +----+----+----+----+     | .. | 11 | 12 | .. |
                                 |               +----+----+----+----+ 
                                 |                         |
                                 +---------+  +------------+
                                           |  |
                                           v  v
                                  Leaf Bucket (32 entries)
                              +------------------------------+
                              | [ 0x7A91_04C2 | @offset   ]  |
                              | [ ...         | ...       ]  |
                              +------------------------------+

@desc A 32-bit hash is consumed in 4-bit slices at each depth level to traverse
routing nodes until reaching the target 32-entry leaf bucket
</fig>

The important part is what happens when that bucket becomes full. Instead of growing
the entire index, we turn just that bucket into a routing node and distribute its
entries across new child buckets using the next four bits of their hashes.

<fig>
BEFORE (Bucket 2 Full)             AFTER (Local Split at Bucket 2)

     Parent Node                            Parent Node
+----+----+----+----+                  +----+----+----+----+
| 0  | 1  | 2  | .. |                  | 0  | 1  | 2  | .. |
+----+----+----+----+                  +----+----+----+----+
|    |        |                        |    |    |
v    v        v                        v    v    v
 [B0] [B1]   +----------------+      [B0] [B1]   +--------------+
(Untouched)  | Bucket 2 (Full)|     (Untouched)  | Routing Node |
             | 32 / 32 entries|                  | (next 4 bits)|
             +----------------+                  +----+----+----+
                                                      |    |    |
                         +----------------------------+    |    |
                         |                +----------------+    |
                         v                v                     v
                  +--------------+ +------------+       +------------+
                  | Bucket 2     | | New Bucket |       | New Bucket |
                  | (Reused: #0) | | (Child #1) |       | (Child ..) |
                  +--------------+ +------------+       +------------+

@desc When a leaf bucket fills up, it is replaced in its parent by a routing node,
redistributing only its 32 entries across the reused bucket and newly allocated child
buckets using the next 4-bit hash slice
</fig>

Everything outside that bucket stays exactly where it was. We don't move the existing
key-value payloads either; only the index entries pointing to them are redistributed.

The original bucket is also reused as one of the children, while the remaining
buckets are newly allocated. So the cost of growing the index is tied to the bucket
being split, rather than the size of the entire database.

This gives us the property we were looking for. A growing database no longer means
growing one giant hash table. A full bucket only affects its own small part of the
index.

**No global rehash. No unrelated entries participating in the growth. I was able to
reduce rehashing to a single bucket instead of the entire bucket.**

## § Conclusion

Now that we have the new index structure in place, the obvious question remains, _how
does it perform?_

When I ran a million consecutive operations for each workload and measured the
latency distribution.

| Workload               | p50     | p90     | p99     | p99.99   |
|:-----------------------|:--------|:--------|:--------|:---------|
| SET (80/20 New/Update) | 1.42 µs | 1.76 µs | 1.37 ms | 5.03 ms  |
| GET (60/40 Hit/Miss)   | 0.87 µs | 1.11 µs | 1.39 µs | 6.18 µs  |
| DEL (60/40 Hit/Miss)   | 1.07 µs | 1.36 µs | 5.00 µs | 11.30 µs |

The read path looks particularly good. Even at **p99.99**, GET latency stays below
**7 µs**, and deletes remain in the low microsecond range.

Writes tell a slightly different story. While median and p90 latencies are quite low,
the upper percentiles are considerably higher. This is not entirely an index problem;
optimistic transaction conflicts and NVMe writeback also contribute to write latency.

_It's worth pointing out that these are end-to-end database benchmarks, and not a
direct isolated comparison between the old and new index implementations._

Still, we achieved the architectural goal we set out for. Growing the index no longer
requires rebuilding the entire structure. A full bucket only affects its own branch,
existing payloads stay where they are, and unrelated entries don't have to
participate.

I know there's still plenty of work to do, particularly around write tail latency,
but I am happy that I was able to eliminate one major source of unpredictable work
from the index.

@references

[^1]: Having everything in a single file serves quite a few purposes. We have fewer
resources to manage, don't need to juggle multiple file handles, and get a much
simpler storage lifecycle. I've actually experimented with splitting the database
across multiple files, _but after more than two years and 900+ commits of trying
things, breaking things, and trying again_, a single memory-mapped file has worked
out good for TurboFox. There were plenty of dead ends along the way, but that's part
of building something yourself.

[^2]: I actually experimented with overflow buckets in an earlier version of
TurboFox. The [README](https://github.com/pid7-org/turbofox/blob/a6294d16b105ed14917d50cf6cbf1b5f5fbcc064/README.md)
contains the benchmark results, and the
[DESIGN.md](https://github.com/pid7-org/turbofox/blob/a6294d16b105ed14917d50cf6cbf1b5f5fbcc064/DESIGN.md)
has more details about the implementation. The results weren't particularly
encouraging. We were seeing around **120 µs** p90 latency, with the far tail reaching
roughly **14.2 ms**. That's quite a difference, and it clearly showed that we had
traded one problem for another. Instead of dealing with expensive insertions, we were
making lookups increasingly expensive. Eventually, I scrapped the approach.
